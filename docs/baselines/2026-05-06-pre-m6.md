# Pre-M6 Baseline — 2026-05-06

## Environment

- Host: vastdataubuntu2404 (VM)
- Storage NIC: ens33, 10 GbE
- Source + destination: selab-var204 cluster (same cluster, different exports)
- Binary: `vamoose worker` from main, commit ebd7040 (m5-pass-vamoose-cli)

## Workload

- 100 files × 100 MB = 10 GB total
- All files in the medium tier (1 MB – 1 GB)
- Generated via M5 harness Phase 1 (parallel dd from /dev/urandom)

## Configuration

Default config from M5 harness, intended values:
- `nfs_connections = 1`
- `pipeline_depth = 1`
- `io_uring_queue_depth = 32`
- `fixed_buffer_count = 32`
- `fixed_buffer_size = 1 MiB`
- `inflight_medium = 1`

**Compiler dead-code warnings indicate these `MoverCfg` fields are not
actually consumed by the mover.** Actual code path is the default
mover, not the configured values.

## Results

| Metric | Value |
|---|---|
| Wall clock (B's migration window) | 45 sec |
| RX sustained | 213.4 MB/s |
| TX sustained | 213.2 MB/s |
| Peak ifutil (per-direction) | 22.7% |
| Total NIC traffic | ~3.4 Gbps |
| % of 10 Gbps full-duplex | ~34% |
| % of per-direction line rate | ~17% |
| Throughput stability | Steady, no stalls or bursts |

## Interpretation

- **RX ≈ TX** as expected for a migration workload (every byte read from
  src is written to dst over the same NIC).
- **~4-5× headroom** to per-direction NIC saturation.
- **Mover is not parallelized through to libnfs/io_uring.** The
  `MoverCfg` knobs the design doc defines are scaffolded but unwired.

## Implications for M6

M6 is **implementation**, not tuning. The work is wiring `MoverCfg`
fields through to actual io_uring + libnfs calls — what the design
doc describes as the M3 milestone, which appears to have shipped as
scaffolding without the perf path implemented.

Expected after M6 implementation:
- 4-5× single-worker throughput on this VM
- Multi-worker on single VM caps at NIC line rate
- Multi-worker scaling proof requires multiple VMs
